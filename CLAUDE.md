# CLAUDE.md

This file provides guidance to Claude Code when working with code in this repository.

## What this project is

**demo3.0-UI** — the same app as `../demo2.0` (Envoy: dispatches AI-driven outbound calls via Vapi/Twilio/Claude to chase overdue invoices, with a Supabase Storage invoice-ingestion + scheduling queue), wearing the visual system of the sibling product `../../EnvoyIn` (dashboard shell with a collapsible dark sidebar, brand-red `#E31E24`, DM Sans + Bricolage Grotesque, hand-rolled component library). Data + files live in Supabase (Postgres + Storage); the Google Drive/Sheets integration that demo2.0 uses was replaced here (see Changelog).

This was a **UI-only reskin + structural rebuild**, not a feature change: the backend is byte-for-byte identical to demo2.0 (see below), and the goal was full functional parity. If demo2.0 gains a new feature, this project will not pick it up automatically — it's a separate copy, not a shared package.

## Working rules

- For any non-trivial task, **plan first** (opus sub-agent / Plan agent), get the plan reviewed, then execute. "Non-trivial" includes anything touching auth, schema, money/payment logic, multi-tenancy scoping, or more than a couple of files — when in doubt, plan.
- **Do not guess on ambiguous points — ask.** Stop and ask a clarifying question whenever a requirement, scope boundary, or existing-behavior assumption is unclear, even mid-task. A wrong guess costs more than a question.
- **Prioritize correctness over speed.** This app handles auth, tenant isolation, and money (invoices/payments) — double-check IDOR/ownerId scoping, role gates, and financial math before considering a change done. Re-read edited files and re-verify assumptions before destructive or hard-to-reverse actions.
- For long or tricky multi-step work, prefer delegating to an opus-backed sub-agent (Plan agent for design, general-purpose for execution) rather than pushing through solo in one pass — it keeps the plan reviewable and reduces mistakes from context overload.
- After any commit that gets pushed, add an entry to the Changelog section below (date, what changed, why) as part of that same push. Keep new entries as tight as the recent ones below — one paragraph of substance, not a blow-by-blow.

## Relationship to demo2.0 and EnvoyIn

- **demo2.0** (`../demo2.0`) — source of truth for all functionality/business logic. This project's `src/lib/*.ts`, `src/app/api/**`, `prisma/schema.prisma`, and `scripts/scheduler.ts` were ported from there with zero logic changes. If a bug is fixed or a feature added in demo2.0's backend, it needs to be manually re-ported here — there's no shared package linking the two.
- **EnvoyIn** (`../../EnvoyIn`) — source of the visual design system (Tailwind theme, `globals.css` utility classes, sidebar shell pattern, component organization), and — as of the 2026-07-22 merge-readiness work — the source of the auth/multi-tenancy/ticket patterns this project now mirrors so it can eventually be merged INTO EnvoyIn. **This project now HAS auth + multi-tenancy** (email+password, `ownerId` = lowercased email on every table) — the old "no auth, matching demo2.0" statement is superseded (see Changelog 2026-07-22 and 2026-08-05).

## First-time setup

```bash
npm install
cp .env.example .env   # fill in DATABASE_URL + DIRECT_URL (Supabase) and the API keys — see below
npm run db:push        # syncs the Prisma schema to Supabase Postgres
npm run dev:all         # web server (:3010) + scheduler worker together
```

For Vapi webhooks locally: `npm run tunnel` (ngrok on :3010), set `PUBLIC_URL` in `.env` to match.

## Commands

```
npm run dev       # Next.js dev server on :3010 (not :3000 — runs alongside demo2.0)
npm run scheduler # Standalone scheduler worker (node-cron via tsx)
npm run dev:all    # dev server + scheduler worker together
npm run build      # prisma generate + next build
npm run db:push    # Push Prisma schema to Supabase Postgres (add --force-reset to rebuild clean)
npm run tunnel      # ngrok http 3010
```

**Windows gotcha:** run `npm run build` with the dev server STOPPED — a running dev server locks the Prisma engine DLL (`EPERM`).

## Environment / database

- **Supabase Postgres** (migrated off local SQLite on 2026-07-21 — see Changelog). Two URLs in `.env`:
  - `DATABASE_URL` — pooled connection (pgbouncer, port 6543, `?pgbouncer=true`) used at runtime.
  - `DIRECT_URL` — direct connection (port 5432) used by `prisma db push` / any DDL.
- The schema is **Prisma-owned** (`prisma db push`, no migrations dir). `--force-reset` drops & rebuilds all tables clean.
- Data is now in a **shared remote DB**, so the old SQLite file-per-app isolation is gone: if demo2.0 (still SQLite) and demo3.0 ever point at the same Supabase project they'd collide. Keep them on separate projects/schemas if both dispatch.
- `.env` holds Vapi/Twilio/Gemini credentials (same as demo2.0) plus the Supabase keys (`DATABASE_URL`, `DIRECT_URL`, `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, `SUPABASE_INVOICE_BUCKET`), plus auth env (`AUTH_SECRET`, `PUBLIC_BASE_URL`, `RESEND_API_KEY`/`RESEND_FROM_EMAIL`). No Google credentials — the Drive/Sheets integration was removed. `PUBLIC_URL` (the ngrok tunnel Vapi posts webhooks to) can only point at one app's port at a time, so only one of demo2.0 / demo3.0-UI should be actively dispatching real calls unless you set up a second tunnel.
- **Files:** invoice PDFs live in the Supabase Storage bucket `invoices` (private; accessed server-side via `SUPABASE_SERVICE_ROLE_KEY`, proxied through `/api/files/*`, keys owner-prefixed). **Customers** (formerly "Contacts") are `customer` rows, managed at `/app/customers`. Helpers: `src/lib/storage.ts`, `src/lib/customers.ts`.
- `.env` is gitignored and has never been committed — keep it that way (it contains live secrets).

## Architecture

### Backend — call flow/scheduling logic still matches demo2.0 (read that project's CLAUDE.md for the full narrative: call flow, scheduling internals, the AI brain in `lib/vapi.ts`). Summary: Vapi (voice orchestration) → Twilio (PSTN) → Claude (LLM brain via Anthropic, configured in the Vapi assistant). `src/lib/dispatcher.ts` holds all grouping/business-hours/concurrency/dispatch logic shared by the HTTP routes and the standalone `scripts/scheduler.ts` worker.

**Persistence diverged from demo2.0 in the Supabase migration** (2026-07-21). The data model is the normalized CRM ERD (`prisma/schema.prisma`, source ERD in `docs/database-erd.md`), with every aggregate root also carrying an `ownerId` (multi-tenancy, added 2026-07-22):
- `Customer` — the debtor. Resolved find-or-create by ABN → fuzzy name via `resolveCustomerId()` in `dispatcher.ts`.
- `Invoice` — ERD invoice columns **plus** the operational scheduling columns (`chaseAfter`, `status`, `attempts`, `groupKey`, caller config) so it still doubles as the queue. `status` includes `stored` (parsed/persisted but not yet queued).
- `InvoiceLineItem` — line items are rows; `serializeLineItems()`/`parseLineItemRows()` in `dispatcher.ts` convert at the API boundary so the parser/prompt/UI still speak the old `{description,quantity,unitPrice,amount}` JSON string.
- `Call` — ERD call columns + denormalized lead-invoice snapshot cols (amountDue/currency/banking/invoiceNumber). `transcript` is native `jsonb`. Linked to invoices via `CallInvoice` join table.
- `Ticket` — one per outbound Call (tagged `outbound`, `channel:"phone"`), EnvoyIn-shaped with a real `customerId` FK.
- `Tenant` — per-owner config (business profile, phone number, members, forecast history, encrypted credentials).
- `Settings` — one row per `ownerId` (was a global singleton pre-multi-tenancy).
- `Payment`, `Note`, `SalesPerson`, `Location` — ERD tables, in active use as of Phase 3 / the CRM-details pass.
- `User`, `Account`, `VerificationToken` — auth tables (see Changelog 2026-08-05 for the current email+password shape).

Prisma **field names were kept identical to demo2.0** (camelCase) and `@map`'d to the ERD's snake_case columns, so the original API JSON contracts were left unchanged where possible. Pragmatic type notes: money is `Float` (double, not `numeric`), dates (`invoiceDate`/`dueDate`) are `text` to preserve string-compare logic. Outstanding-balance math lives in `src/lib/money.ts` (per-currency, computed in code — see Changelog 2026-07-24).

### UI — real routes + shared component library (the structural change from demo2.0)

demo2.0's entire UI lived in one ~4,000-line `src/app/page.tsx` with in-memory screen-switching (no routing). This project restructured that into real Next.js routes under `src/app/app/*` (dashboard, calls/new, calls/live/[id], invoices/select, invoices/bulk, customers, customers/[id], payments, queue, forecasting, analytics, settings), a sidebar shell (`AppShellChrome.tsx`), and a shared component library:

```
src/components/shared/   — Icons, Button, Card, Badge, Toast, ConfirmDialog, Skeleton, Drawer, Modal,
                            Spinner, WaveformViz, Logo, Hairline, TicketBoard, charts/Charts.tsx, plus
                            feature-shared pieces:
                              - InvoiceComposeForm.tsx  — parsed-invoice review/edit form, reused across
                                the new-invoice page, bulk-item edit drawer, and queue-invoice edit drawer
                              - CallDetailDrawer.tsx / TicketDetailDrawer.tsx / InvoiceDetailDrawer.tsx
                              - BulkIntakeContext.tsx   — in-flight bulk-upload/parse/dispatch state,
                                lifted into a context (mounted in app/layout.tsx) so it survives navigation
                                between /app/invoices/select and /app/invoices/bulk
src/lib/
  format.ts, client-types.ts        — formatting helpers and frontend types, ported from demo2.0
  prisma.ts, vapi.ts, dispatcher.ts, sms.ts, nameUtils.ts   — ported from demo2.0
  storage.ts, customers.ts, tickets.ts, invoices.ts, invoice-ingest.ts, money.ts,
  payments.ts, credentials.ts, forecasting.ts, analytics.ts, access.ts, members.ts,
  permissions.ts, page-guard.ts, auth-adapter.ts, tenant.ts   — demo3.0-specific (see Changelog)
```

Detail/edit overlays (call detail, ticket detail, invoice detail, bulk/queue-invoice edit) are `Drawer` overlays (slide-in from the right), matching EnvoyIn's `TicketDetail` drawer pattern — inspect-in-place rather than navigate-away.

### Design tokens

`src/app/globals.css` — EnvoyIn's `@layer components` classes (`.card`, `.btn-primary/secondary/ghost/danger`, `.input`, `.label`, `.badge`, `.pill`), `.app-bg`/`.sidebar-bg` backgrounds, brand-red Tailwind extension (`tailwind.config.ts`), plus gradient/tilt/reveal animation classes ported from EnvoyIn for the dashboard and landing page. Demo2.0's own animations with no EnvoyIn equivalent (`wave-bar`, `dot-pulse`, `pulse-ring`, `fade-up`/`fade-in`) were kept and recolored to brand red — they're load-bearing for the Live screen. Demo2.0's cream/burgundy palette, Fraunces/Geist fonts, and `.grain` texture were dropped entirely.
